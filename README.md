# BidSignal

공공입찰 공고 관리 · 마감 알림 서비스

BidSignal은 나라장터 공고를 매시간 수집하고, 관심 공고 저장부터 마감 알림, 입찰 준비 체크리스트, 공고문 요약까지 관리하는 서비스입니다.

공공 SI에서 나라장터 관련 개발을 하면서 공고 데이터와 입찰 업무 흐름을 다뤄봤습니다. 공고를 조회하는 것뿐 아니라, 관심 있는 공고를 모아두고 마감 전까지 준비 상태를 관리하는 흐름을 직접 만들어보고 싶었습니다.

🔗 [bidsignal.kr](https://bidsignal.kr)

GitHub Actions에서 빌드와 테스트가 통과하면 Lightsail 서버에서 최신 코드를 받아 다시 배포합니다. UptimeRobot은 서버 밖에서 5분마다 `/actuator/health`를 확인하고, 상태가 정상이 아니면 이메일로 알려줍니다.

## 핵심 기능

### 1. 나라장터 공고 수집 및 검색

나라장터 OpenAPI를 매시간 조회해 공고를 수집하고 서비스 안에서 검색할 수 있게 만들었습니다.

공고번호와 공고차수를 기준으로 중복 여부를 확인하고, DB에도 유니크 제약을 걸어 중복 저장을 막았습니다.

사용자는 공고명, 공고유형, 금액 범위, 마감일로 검색할 수 있고, 마감된 공고 포함 여부도 선택할 수 있습니다.

### 2. 관심 공고 관리

입찰을 여러 건 동시에 준비할 때 진행 상황을 기록할 수 있도록 관심 공고 저장, 상태 변경, 메모 기능을 만들었습니다.

관심 공고 목록에서는 각 공고의 체크리스트 진행률도 함께 확인할 수 있습니다.

### 3. 마감 임박 이메일 알림

관심 공고 중 상태가 `검토중` 또는 `준비중`인 공고를 대상으로 마감 D-3, D-1 이메일 알림을 발송합니다.

매일 오전 9시에 실행하며, 발송 이력을 남겨 같은 공고의 같은 D-day 알림이 중복 발송되지 않도록 했습니다.

메일은 발송 후 DB 트랜잭션을 롤백하더라도 취소할 수 없기 때문에, 전체 발송을 하나의 트랜잭션으로 묶지 않고 공고별 성공/실패 이력을 남겼습니다.

### 4. 입찰 준비 체크리스트

관심 공고를 저장하면 낙찰방법명, 낙찰방법 적용기준, 계약체결방법에 따라 6종 템플릿 중 하나를 선택해 체크리스트를 자동 생성합니다.

- 기본 입찰 준비
- 소액수의/수의계약
- 적격심사
- 협상에 의한 계약
- 규격가격/2단계 평가
- 종합심사/종합평가

이후 공고유형, 제출방식, 평가비율 등을 보고 필요한 항목을 추가합니다. 예를 들어 협상에 의한 계약은 제안서와 발표자료 위주로 구성하고, 공사 공고에는 면허와 실적 확인 항목을 추가합니다.

관심 공고 목록에서 진행률을 보여줄 때는 공고별로 체크리스트를 다시 조회하지 않고, 관심 공고 ID 목록으로 항목을 한 번에 조회한 뒤 메모리에서 진행률을 계산합니다.

### 5. 공고문 AI 요약

나라장터 공고에는 금액, 마감일 같은 정보가 이미 구조화되어 있습니다. AI 요약에서는 이런 정보를 반복하지 않고, 공고문을 직접 읽어야 알 수 있는 참가자격 제한, 추가 제출서류, 특수 절차 등을 정리하도록 했습니다.

나라장터 API에서 제공하는 표준공고서 URL을 요약 대상으로 사용합니다. 파일 URL에 확장자가 없는 경우가 있어 다운로드한 파일의 바이트 시그니처로 HWP, HWPX, PDF를 구분합니다.

- HWP: OLE2 시그니처, `hwplib` 사용
- HWPX: ZIP 기반 문서, `hwpxlib` 사용
- PDF: `%PDF` 시그니처, `PDFBox` 사용

HWP/HWPX는 미리보기 텍스트가 아니라 문서 본문을 추출합니다. HWPX로 읽을 수 없는 ZIP 파일은 내부에서 HWP, HWPX, PDF 파일을 다시 찾아 처리하도록 했습니다.

추출한 텍스트는 Gemini API로 요약하며, 프롬프트에는 원문에 없는 내용을 추측하지 않도록 조건을 넣었습니다.

## 설계 의사결정

### JWT + Redis Refresh Token

Access Token만 사용하면 로그아웃해도 이미 발급된 토큰은 만료 전까지 유효합니다.

그래서 Access Token은 별도로 저장하지 않고, Refresh Token만 Redis에 저장했습니다. 사용자 ID를 키로 사용하고 토큰 만료 시간에 맞춰 TTL을 설정했습니다.

재발급할 때는 요청으로 받은 Refresh Token과 Redis에 저장된 값을 비교합니다. 로그아웃이나 회원탈퇴 시 Redis의 토큰을 삭제해 추가 재발급을 막습니다. 이미 발급된 Access Token까지 즉시 무효화하는 구조는 아닙니다.

### WebClient 대신 RestClient를 선택한 이유

나라장터와 Gemini API 호출은 요청을 보내고 응답을 받는 방식이고, 백엔드는 Spring MVC 기반입니다.

현재 구조에서는 WebClient를 추가하기보다 RestClient로 구현하는 편이 단순하다고 판단했습니다. 비동기 처리가 꼭 필요한 상황은 아니어서 기존 구조에 맞춰 선택했습니다.

### 체크리스트에 AI를 쓰지 않은 이유

처음에는 체크리스트도 AI로 고도화하려고 했습니다. 그런데 기존 로직을 다시 보니 낙찰방법, 계약방법, 제출방식, 공고유형 조합만으로도 필요한 항목을 어느 정도 만들 수 있었습니다.

AI를 추가해도 같은 내용을 자연어로 다시 설명하는 데 그칠 것 같아서 체크리스트는 규칙 기반으로 유지했습니다. 대신 원문을 읽어야 의미가 있는 공고문 요약에 AI를 사용했습니다.

### 공고 수집과 AI 요약 처리 분리

공고 수집은 정해진 주기에 API 데이터를 가져와 저장하는 작업이고, AI 요약은 파일 다운로드, 문서 파싱, 외부 API 호출이 필요한 작업입니다.

처리 성격이 달라 각각 별도 스케줄러 메서드로 나누고 실행 주기도 다르게 설정했습니다. 수집은 매시간 실행하고, 요약은 이전 작업이 끝난 뒤 15초 후 요약되지 않은 공고 한 건을 처리합니다.

### AI 요약 실패 상태 관리

처음에는 요약에 실패하면 `ai_summary`가 `NULL`로 남았습니다. 스케줄러는 `NULL`인 공고를 다시 조회하기 때문에, 요약할 수 없는 공고를 계속 처리하는 문제가 있었습니다.

그래서 `NULL`은 처리 전, 빈 문자열은 요약을 시도했지만 결과를 만들지 못한 상태로 구분했습니다. 지금은 실패한 공고를 자동 재시도하지 않고 넘어가는 방식입니다.

또 요약 대상을 반복 조회하는 쿼리에 `ai_summary`, `std_ntce_doc_url` 복합 인덱스를 추가했습니다. 실제 대용량 데이터에서 성능을 비교한 단계까지는 아닙니다.

### 단일 서버 운영과 메모리 제한

백엔드는 AWS Lightsail 2GB RAM 서버에서 운영하고 있습니다.

자원이 넉넉하지 않아 Docker Compose에서 애플리케이션, PostgreSQL, Redis에 각각 메모리 제한을 걸고, JVM 힙 크기도 제한했습니다.

작은 서버에서 여러 프로세스를 같이 운영하면서 자원 사용을 신경 써야 한다는 점을 배웠습니다.

### 서비스 상태 확인과 외부 모니터링

공고 수집이 에러 없이 멈춘 일을 겪은 뒤, 서버가 켜져 있는지만 확인해서는 부족하다고 생각했습니다.

Spring Boot Actuator의 `/actuator/health`에 공고 수집 성공 여부를 확인하는 항목을 추가했습니다. 5개 공고유형을 모두 에러 없이 조회했을 때만 마지막 성공 시각을 갱신하고, 3시간 동안 성공하지 못하면 `DOWN`(HTTP 503)을 반환합니다.
수집이 매시간 실행되기 때문에 일시적인 실패 한두 번은 넘기고, 계속 실패할 때만 걸리도록 3시간으로 잡았습니다. 이 값은 운영하면서 조정할 계획입니다.

성공 시각은 DB가 아니라 메모리에 저장합니다. 앱이 재시작되면 현재 시각으로 초기화되므로 재시작 직후에는 실제 수집 성공 여부를 바로 판단하지 못하는 한계가 있습니다.

서버 자체가 내려가는 경우도 감지하려고 UptimeRobot에서 외부 요청을 보내도록 했습니다. 앱을 중지했을 때와 상태 확인 기준 시간을 임시로 줄였을 때 알림 메일이 오는 것을 확인했습니다. 실제 API 실패 상황을 직접 재현해 검증한 것은 아닙니다.

## 트러블슈팅

### 1. 공고 수집이 에러 없이 멈춤

운영 중 DB를 확인하다가 저장된 공고의 마지막 등록일이 현재보다 한참 이전이라는 것을 발견했습니다.

컨테이너는 정상적으로 실행 중이었고 에러 로그도 없었습니다. 수집 로그를 확인하니 어느 시점부터 "공고 수집 스케줄러 시작"만 남고 "종료" 로그가 없었습니다. 그 뒤로는 다음 정시 실행 로그도 남지 않았습니다.

JVM 스레드 덤프를 확인해 보니 수집 스케줄러 스레드가 나라장터 API 응답을 기다리고 있었습니다. 외부 API를 호출하는 `RestClient`에 타임아웃을 설정하지 않아 응답이 지연될 때 작업이 계속 대기하고 있었던 것입니다.

연결 제한 시간 5초, 응답 제한 시간 30초를 설정했습니다.

```java
HttpClient httpClient = HttpClient.newBuilder()
        .connectTimeout(Duration.ofSeconds(5))
        .build();

JdkClientHttpRequestFactory requestFactory = new JdkClientHttpRequestFactory(httpClient);
requestFactory.setReadTimeout(Duration.ofSeconds(30));

RestClient restClient = RestClient.builder()
        .baseUrl(naraApiProperties.getBaseUrl())
        .requestFactory(requestFactory)
        .build();
```

공고유형별 수집은 `try-catch`로 처리하고 있어 한 유형이 실패해도 나머지 유형은 이어서 처리합니다. 수정 후에는 정시 실행이 시작부터 종료까지 이어지는 것을 로그로 확인했습니다.

이 일을 계기로 에러가 발생했는지뿐 아니라, 정해진 작업이 최근에 성공했는지도 확인할 수 있도록 상태 확인 기능을 추가했습니다.

### 2. AI 요약이 DB에 저장되지 않음

Gemini API 호출은 성공했는데 DB의 `ai_summary`는 계속 `NULL`로 남아 있었습니다.

처음에는 스케줄러에서 엔티티를 조회한 뒤 서비스 메서드로 넘겼습니다.

```java
Notice notice = noticeRepository.findById(id).orElseThrow();
noticeSummaryService.getSummary(notice);
```

스케줄러에서 조회한 엔티티는 repository 조회 트랜잭션이 끝난 뒤 준영속 상태가 됐고, 서비스의 `@Transactional` 메서드에 전달해도 변경 감지가 동작하지 않았습니다.

서비스가 엔티티 대신 ID를 받도록 바꾸고, `@Transactional` 메서드 안에서 공고를 다시 조회한 뒤 수정하도록 변경했습니다.

```java
@Transactional
public String getSummary(Long noticeId) {
    Notice notice = noticeRepository.findById(noticeId).orElseThrow();

    ...

    notice.updateAiSummary(summary);
    return summary;
}
```

이후에는 변경 감지로 `UPDATE`가 실행되는 것을 확인했습니다. 엔티티를 어디에서 조회했고, 수정하는 시점에 영속성 컨텍스트가 유지되는지가 중요하다는 것을 알게 됐습니다.

### 3. 서버 시간대 때문에 공고 수집 구간이 어긋남

수집은 정상적으로 실행되는데, 오후 5시가 넘은 시간에도 그날 저장된 마지막 공고는 오전 7시대였습니다.

Lightsail 서버와 컨테이너가 UTC 시간대로 동작하고 있었습니다. 수집 코드에서는 `LocalDateTime.now()`로 오늘 0시부터 현재까지의 조회 구간을 만들었는데, 나라장터 API는 전달된 시간을 한국 시간으로 해석하기 때문에 실제보다 약 9시간 이전까지 조회하고 있었습니다.

코드에서 현재 시각을 구할 때 한국 시간대를 명시하도록 바꿨습니다.

```java
LocalDateTime now = LocalDateTime.now(ZoneId.of("Asia/Seoul"));
```

JPA Auditing에서 자동으로 기록하는 시간도 맞추기 위해 Docker Compose의 앱 컨테이너에 `TZ: Asia/Seoul`을 설정했습니다.

수정 후에는 같은 날 오후에 등록된 공고까지 저장되는 것을 DB에서 확인했습니다.

## 회고

나라장터 관련 개발을 하면서 접했던 공공입찰 도메인에서 시작한 프로젝트입니다. 공고 조회 이후에 관심 공고를 관리하고 입찰을 준비하는 흐름을 직접 구현해볼 수 있었습니다.

가장 기억에 남는 작업은 공고문 AI 요약과 공고 수집 장애 해결입니다. AI 요약에서는 어떤 부분에 AI가 필요한지 다시 판단했고, 문서 형식에 따라 본문을 추출하는 작업도 직접 해봤습니다.

운영하면서는 컨테이너가 정상이어도 실제 기능이 멈출 수 있다는 것을 겪었습니다. 이후 타임아웃을 설정하고 수집 성공 여부를 외부에서 확인하도록 바꿨습니다. 단순히 배포하는 것에서 끝나지 않고, 문제가 생겼을 때 알아챌 방법까지 생각해보게 됐습니다.

아쉬운 점도 있습니다. 지금은 요약 실패 상태를 빈 문자열로 구분할 뿐 재시도나 실패 원인을 따로 관리하지 못합니다. 다음에는 처리 상태를 분리해서 재시도가 필요한 경우와 요약할 수 없는 경우를 나누고 싶습니다.

모니터링도 현재는 서비스 상태와 공고 수집 성공 여부 중심입니다. 앞으로는 요청별 오류와 서버 자원 사용까지 확인할 수 있게 보완할 계획입니다.
