# BidSignal

공공입찰 공고 관리 · 마감 알림 서비스

BidSignal은 나라장터 공고를 매시간 수집하고, 관심 공고 저장부터 마감 알림, 입찰 준비 체크리스트, 공고문 요약까지 이어지는 흐름을 관리하기 위해 만든 서비스입니다.

공공 SI에서 나라장터 관련 개발을 하면서 공고 데이터와 입찰 업무 흐름을 다뤄봤습니다. 공고마다 확인해야 할 정보는 많은데, 관심 공고를 따로 모아두고 마감 전까지 준비 상태를 이어가는 흐름은 직접 만들어볼 만한 주제라고 생각했습니다.

BidSignal은 그 경험을 바탕으로, 공고 조회 이후의 준비 과정을 개인 프로젝트로 풀어본 서비스입니다.

🔗 [bidsignal.kr](https://bidsignal.kr)

## 핵심 기능

### 1. 나라장터 공고 수집 및 검색

나라장터 사이트는 공고 수가 많고 검색 필터도 제한적이라, 원하는 조건의 공고만 골라보기가 번거롭습니다. OpenAPI를 매시간 조회해서 공고를 미리 수집해두고, 서비스 안에서 검색할 수 있게 만들었습니다.

공고번호와 공고차수를 기준으로 이미 저장된 공고인지 확인하고, DB에도 유니크 제약을 걸어 같은 공고가 중복 저장되지 않도록 했습니다.

사용자는 공고명, 공고유형, 금액 범위, 마감일 기준으로 공고를 검색할 수 있고, 마감된 공고 포함 여부도 선택할 수 있습니다.

### 2. 관심 공고 관리

입찰을 여러 건 동시에 준비하다 보면 어떤 공고를 얼마나 진행했는지 따로 기록해둘 곳이 필요합니다. 사용자가 입찰 준비가 필요한 공고를 관심 공고로 저장하고, 상태와 메모를 남길 수 있게 했습니다.

저장된 관심 공고 목록에서는 체크리스트 진행률도 함께 확인할 수 있습니다.

### 3. 마감 임박 이메일 알림

여러 공고를 동시에 챙기다 보면 마감을 놓치는 게 가장 큰 리스크입니다. 관심 공고 중 준비 상태가 `검토중` 또는 `준비중`인 공고를 대상으로 마감 D-3, D-1 이메일 알림을 발송합니다.

알림은 매일 오전 9시에 실행되며, 발송 이력을 저장해 같은 공고에 같은 D-day 알림이 중복 발송되지 않도록 했습니다.

메일 발송은 외부 시스템이라 롤백할 수 없기 때문에, 전체 과정을 하나의 트랜잭션으로 묶지 않고 공고별로 성공/실패 이력을 남기도록 구성했습니다.

### 4. 입찰 준비 체크리스트

입찰마다 낙찰방법이나 계약방법에 따라 준비해야 할 서류가 달라서, 공고를 볼 때마다 뭘 챙겨야 하는지 매번 다시 확인해야 하는 번거로움이 있습니다. 관심 공고를 저장하면 기본 체크리스트를 자동 생성하도록 했습니다.

낙찰방법명, 낙찰방법 적용기준, 계약체결방법을 기준으로 6종 템플릿 중 하나를 선택합니다.

* 기본 입찰 준비
* 소액수의/수의계약
* 적격심사
* 협상에 의한 계약
* 규격가격/2단계 평가
* 종합심사/종합평가

이후 공고유형, 제출방식, 평가비율 같은 조건을 보고 보조 항목을 추가합니다.

예를 들어 협상에 의한 계약이면 제안서, 가격제안서, 발표자료 중심으로 항목을 만들고, 공사 공고라면 면허 및 실적 조건 확인 항목을 추가합니다.

관심 공고 목록에서는 각 공고의 체크리스트를 하나씩 다시 조회하지 않고, 여러 관심 공고의 체크리스트 항목을 한 번에 가져와 진행률을 계산했습니다.

### 5. 공고문 AI 요약

공고문 원문은 관료적인 문장이 많고 분량도 길어서, 정작 이 공고만의 특이사항(참가자격 제한, 추가 제출서류, 특수 절차 등)을 놓치기 쉽습니다. 원문을 요약해서 보여주는 기능을 추가했습니다.

나라장터 공고에는 이미 금액, 마감일, 개찰일시 같은 구조화된 정보가 있습니다.
그래서 AI 요약은 화면에 이미 보이는 정보를 다시 요약하는 데 쓰지 않고, 공고문 원문에만 있는 내용을 정리하는 데 사용했습니다.

요약 대상은 표준공고서 URL을 기준으로 잡았습니다. 나라장터 API 응답에는 첨부파일 URL이 여러 개 들어오지만, 어떤 파일이 실제 공고문 원본인지 구분하기 어렵습니다. API 스펙에서 표준공고서 URL 필드를 확인했고, 이 값을 요약 대상 파일로 사용했습니다.

공고문 파일은 URL만 보고는 확장자를 알 수 없어서, 다운로드한 파일의 바이트 시그니처를 기준으로 HWP, HWPX, PDF를 판별했습니다.

* HWP: OLE2 시그니처
* HWPX: ZIP 기반 문서
* PDF: `%PDF` 시그니처

HWP는 `hwplib`, HWPX는 `hwpxlib`, PDF는 `PDFBox`로 본문을 추출한 뒤 Gemini API로 요약합니다.

프롬프트에서는 공고명, 금액, 마감일처럼 이미 화면에 있는 정보는 제외하고, 참가자격 제한, 추가 제출서류, 현장설명회, 특수 절차처럼 공고문을 직접 읽어야 알 수 있는 내용만 정리하도록 제한했습니다.

## 설계 의사결정

### JWT + Redis Refresh Token

Access Token은 서버에 상태를 남기지 않아도 되는 장점이 있지만, 그것만 사용하면 로그아웃이나 회원탈퇴 시 이미 발급된 토큰을 서버에서 제어하기 어렵습니다.

그래서 Access Token은 stateless하게 사용하고, Refresh Token만 Redis에 저장했습니다.
Redis에는 사용자 ID를 키로 Refresh Token을 저장하고, 토큰 만료 시간과 동일하게 TTL을 설정했습니다.

로그아웃하거나 회원탈퇴하면 Redis에 저장된 Refresh Token을 삭제합니다.
Access Token 재발급 요청이 들어오면 클라이언트가 보낸 Refresh Token과 Redis에 저장된 값을 비교해서, 서버가 알고 있는 토큰일 때만 새 Access Token을 발급합니다.

### WebClient 대신 RestClient를 선택한 이유

나라장터 API와 Gemini API 호출은 모두 요청-응답 흐름이 단순합니다.
현재 백엔드는 Spring MVC 기반으로 구성되어 있고, 공고 수집과 요약도 스케줄러에서 순차적으로 처리합니다.

이 상황에서는 WebClient를 추가해서 리액티브 스타일을 섞기보다, 기존 서블릿 스택과 잘 맞는 RestClient로 구현하는 쪽이 더 단순하다고 판단했습니다.

“최신 기술을 쓰는 것”보다 지금 구조에서 읽기 쉽고 유지하기 쉬운 선택을 우선했습니다.

### 체크리스트에 AI를 쓰지 않은 이유

처음에는 체크리스트도 AI로 고도화하려고 했습니다.
그런데 기존 체크리스트 로직을 다시 보니 낙찰방법, 계약방법, 제출방식, 공고유형 조합만으로도 어느 정도 필요한 항목을 만들 수 있었습니다.

여기에 AI를 붙이면 같은 내용을 자연어로 다시 말하는 정도에 그칠 것 같았습니다.
그래서 체크리스트는 rule 기반으로 유지하고, AI는 실제로 원문을 읽어야 의미가 있는 공고문 요약에 사용하는 쪽으로 방향을 바꿨습니다.

AI를 넣었다는 사실보다, 어디에 쓰는 게 맞는지 판단하는 게 더 중요하다고 봤습니다.

### 공고 수집과 AI 요약 스케줄러 분리

공고 수집과 AI 요약은 성격이 다릅니다.

공고 수집은 정해진 시간에 나라장터 API를 조회해서 빠르게 저장하는 작업입니다.
반면 AI 요약은 파일 다운로드, 문서 파싱, Gemini API 호출이 들어가서 실패 가능성도 높고 처리 시간도 길 수 있습니다.

두 작업을 하나의 흐름으로 묶으면 요약 처리 때문에 공고 수집까지 늦어질 수 있습니다.
그래서 공고 수집은 매시간 실행하고, AI 요약은 별도 스케줄러에서 요약이 없는 공고를 하나씩 처리하도록 분리했습니다.

AI 요약 스케줄러는 한 번에 여러 건을 몰아서 처리하지 않고, 이전 작업이 끝난 뒤 15초 후 다음 공고를 처리합니다.
간격은 Gemini 무료 티어의 분당 요청 수보다 하루 요청 한도를 기준으로 정했습니다. 하루 공고량 대비 여유 있게 처리되면서도, API 요청이 한 번에 몰리지 않도록 하기 위한 구조입니다.

### 실패한 요약도 처리 완료 상태로 구분

AI 요약은 외부 API와 파일 파싱이 함께 들어가는 작업이라 실패할 수 있는 지점이 많습니다.

* 표준공고서 URL이 비어 있는 경우
* 파일 다운로드에 실패한 경우
* 지원하지 않는 파일 형식인 경우
* 문서 본문 추출에 실패한 경우
* Gemini API 호출에 실패한 경우

처음에는 요약에 실패하면 `ai_summary`가 계속 `NULL`로 남았습니다.
그런데 스케줄러는 “요약이 없는 공고”를 계속 조회하기 때문에, 실패한 공고가 다음 실행에서도 다시 잡히는 문제가 생겼습니다.

그래서 실패한 경우에도 `ai_summary`에 빈 문자열을 저장했습니다.
이렇게 해서 “아직 처리 안 함”과 “처리했지만 요약 없음”을 구분했습니다.

### 반복 실행 쿼리에 인덱스 추가

AI 요약 스케줄러는 15초마다 “요약이 없고 표준공고서 URL이 있는 공고 하나”를 조회합니다.

현재 데이터가 많지 않을 때는 인덱스가 없어도 문제가 크지 않지만, 이 쿼리는 서비스가 실행되는 동안 계속 반복됩니다.
데이터가 늘어난 뒤에야 문제가 보이는 유형이라고 판단해서, 처음부터 `ai_summary`, `std_ntce_doc_url` 기준 복합 인덱스를 추가했습니다.

아직 대용량 튜닝까지 한 것은 아니지만, 반복 실행되는 쿼리는 초반부터 신경 쓰는 게 맞다고 봤습니다.

### 단일 서버 운영에서 메모리 제한

백엔드는 AWS Lightsail 2GB RAM 서버에서 운영했습니다.
서버 자원이 넉넉하지 않기 때문에 Docker Compose에서 애플리케이션, PostgreSQL, Redis 컨테이너에 각각 메모리 제한을 걸었습니다.

애플리케이션 컨테이너에는 JVM 옵션으로 최대 힙 크기를 제한했고, PostgreSQL과 Redis도 컨테이너 단위로 메모리를 제한했습니다.

큰 규모의 인프라는 아니지만, 작은 서버에서 여러 프로세스를 같이 운영할 때 어떤 부분을 제한해야 하는지 직접 경험해볼 수 있었습니다.

## 트러블슈팅

### 1. AI 요약이 DB에 저장되지 않음

Gemini API 호출은 정상적으로 성공했는데, DB의 `ai_summary` 컬럼은 계속 `NULL`로 남아 있었습니다.

처음 구조는 스케줄러에서 공고를 먼저 조회한 뒤, 조회한 엔티티를 서비스 메서드로 넘기는 방식이었습니다.

```java
Notice notice = noticeRepository.findById(id).orElseThrow();
noticeSummaryService.getSummary(notice);
```

문제는 이 엔티티가 이미 준영속 상태였다는 점이었습니다.

`findById()`가 repository 메서드 안에서 자체 트랜잭션으로 실행되고 끝나면, 반환된 엔티티는 영속성 컨텍스트 밖에 있게 됩니다.
이 상태의 엔티티를 다른 `@Transactional` 메서드로 넘겨도, 그 트랜잭션의 영속성 컨텍스트가 조회한 엔티티가 아니기 때문에 변경 감지가 동작하지 않았습니다.

해결 방법은 서비스 메서드가 엔티티가 아니라 ID를 받도록 바꾸는 것이었습니다.

```java
@Transactional
public String getSummary(Long noticeId) {
    Notice notice = noticeRepository.findById(noticeId).orElseThrow();

    String summary = generateSummary(notice);
    notice.updateAiSummary(summary);

    return summary;
}
```

이렇게 바꾸니 조회와 수정이 같은 트랜잭션 안에서 일어나고, JPA 변경 감지로 정상적으로 UPDATE가 나갔습니다.

이후로 트랜잭션 안에서 수정해야 하는 로직은 엔티티를 밖에서 받아오기보다, ID를 받아서 서비스 내부에서 다시 조회하는 방식으로 통일했습니다.

### 2. 실패한 요약 요청이 계속 반복됨

요약 스케줄러는 “요약이 없고 표준공고서 URL이 있는 공고 하나”를 15초마다 가져와 처리합니다.

그런데 로그를 보니 특정 공고 하나가 계속 반복 처리되고 있었습니다.

원인은 `stdNtceDocUrl`이 빈 문자열인 공고였습니다.
조회 조건은 `NOT NULL`만 확인하고 있었기 때문에 빈 문자열도 대상에 포함됐습니다.
서비스 로직에서는 `isBlank()`로 걸러 실패 처리했지만, 실패 후에도 `ai_summary`가 `NULL`로 남아 있어서 다음 스케줄러 실행 때 같은 공고가 다시 조회됐습니다.

해결은 단순하게 했습니다.
요약할 수 없는 경우에도 `ai_summary`에 빈 문자열을 저장했습니다.

이후 스케줄러는 해당 공고를 다시 가져오지 않았고, “요약 대기 상태”와 “요약 불가 상태”를 구분할 수 있게 됐습니다.

### 3. 확장자 없는 나라장터 첨부파일 처리

나라장터에서 내려주는 파일 URL은 확장자가 없는 형태였습니다.
그래서 URL만 보고 HWP인지, HWPX인지, PDF인지 판단할 수 없었습니다.

처음에는 파일명이나 URL에 의존하려고 했지만, 실제 데이터에서는 일관성이 떨어졌습니다.
그래서 파일을 직접 다운로드한 뒤, 파일 앞부분의 바이트 시그니처를 보고 형식을 판별했습니다.

* HWP는 OLE2 기반 시그니처
* HWPX는 ZIP 시그니처
* PDF는 `%PDF` 시그니처

HWPX는 ZIP 기반 문서라서 먼저 HWPX 파서로 읽어보고, 실패하면 ZIP 내부 엔트리에서 다시 HWP, HWPX, PDF 파일을 찾도록 처리했습니다.

처음에는 HWP/HWPX 내부의 미리보기 텍스트만 뽑는 방식도 생각했지만, 실제 공고문에서는 뒤쪽 특수조건이나 제출서류 안내가 잘릴 수 있었습니다.
그래서 미리보기 텍스트가 아니라 문서 본문 전체를 추출하는 방식으로 바꿨습니다.

### 4. 브라우저에서만 발생한 CORS 오류

백엔드 API를 `curl`로 호출하면 정상 응답이 왔지만, 브라우저에서 인증이 필요한 API를 호출하면 CORS 오류가 발생했습니다.

원인은 preflight 요청이었습니다.

브라우저는 `Authorization` 헤더가 포함된 요청을 보내기 전에 `OPTIONS` 요청을 먼저 보냅니다.
그런데 Spring Security 설정에서 모든 요청에 인증을 요구하고 있어서, 실제 요청이 보내지기도 전에 `OPTIONS` 요청이 막히고 있었습니다.

해결은 `OPTIONS` 요청을 인증 없이 통과시키는 규칙을 먼저 추가하는 것이었습니다.

```java
.requestMatchers(HttpMethod.OPTIONS, "/**").permitAll()
```

이후 브라우저에서도 인증 API 요청이 정상적으로 동작했습니다.

### 5. 체크리스트 진행률 조회 시 N+1 방지

관심 공고 목록에는 각 공고의 체크리스트 진행률이 함께 표시됩니다.

공고마다 체크리스트를 따로 조회하면 관심 공고가 20개일 때 체크리스트 조회도 20번 나가는 구조가 됩니다.

그래서 관심 공고 ID 목록을 먼저 모은 뒤, 체크리스트 항목을 한 번에 조회했습니다.
그 결과를 메모리에서 공고별 총 항목 수와 완료 항목 수로 집계해서 진행률을 만들었습니다.

목록 화면에서 필요한 값은 상세한 체크리스트 전체가 아니라 진행률이기 때문에, 이 방식이 더 단순하고 효율적이었습니다.

## 회고

이 프로젝트는 나라장터 관련 개발을 하면서 접했던 공공입찰 도메인에서 출발했습니다.

나라장터에는 공고 데이터가 계속 쌓이고, 각 공고마다 마감일, 참가자격, 제출서류, 첨부 공고문처럼 확인해야 할 정보가 많습니다. 단순히 공고를 조회하는 것보다 “관심 있는 공고를 따로 모아두고, 마감 전에 다시 확인하고, 준비해야 할 항목을 정리하는 흐름”이 필요하다고 생각했습니다.

가장 기억에 남는 작업은 AI 요약 기능이었습니다.

처음에는 체크리스트를 AI로 고도화하려고 했지만, 기존 rule 기반 로직을 다시 보니 낙찰방법, 계약방법, 제출방식, 공고유형 조합만으로도 필요한 항목을 어느 정도 만들 수 있었습니다. 여기에 AI를 붙이면 같은 내용을 자연어로 다시 말하는 수준에 그칠 것 같았습니다.

그래서 체크리스트는 rule 기반으로 유지하고, AI는 실제로 원문을 읽어야 의미가 있는 공고문 요약에 사용하는 쪽으로 방향을 바꿨습니다.

이 과정에서 HWP/HWPX/PDF 문서 파싱, 외부 API 호출, 스케줄러 분리, 실패 상태 관리, JPA 영속성 컨텍스트 문제까지 직접 겪었습니다. 단순히 기능을 붙이는 것보다, 실패했을 때 같은 작업이 계속 반복되지 않게 만들고, 배치 흐름이 서로 영향을 주지 않게 나누는 부분에서 많이 배웠습니다.

아쉬운 점도 있습니다.

현재는 공고 수집과 요약이 모두 폴링 기반입니다. 다음에는 요약 대기 상태를 별도 테이블이나 큐로 분리해서 처리 상태를 더 명확하게 관리해보고 싶습니다.

또 지금은 단일 서버에서 Docker Compose로 운영하고 있지만, 이후에는 배포 자동화, 모니터링, 로그 관리까지 붙여서 운영 쪽 경험도 더 넓혀볼 계획입니다.
